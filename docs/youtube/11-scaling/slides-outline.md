## Слайд 3 — Вертикальное vs горизонтальное (2:00)
**Заголовок:** Два пути масштабирования  
**Контент (две колонки):**

| Вертикальное | Горизонтальное |
|---|---|
| Больше CPU/RAM | Больше серверов |
| Простое | Сложнее |
| Лимит железа | Бесконечно |
| Single point of failure | Отказоустойчивость |

**Вывод:** Мы выбрали горизонтальное — покажем как

## Слайд 4 — Архитектура «до» (3:00)

**Визуал:** Диаграмма: 1 сервер (Node.js + PostgreSQL + Redis)

## Слайд 5 — Архитектура «после» (4:00)

**Визуал:** Диаграмма кластера (из `diagrams-list.md`)  
**Компоненты:**

- Redis (координация + кэш)

---

## Слайд 6 — Главная проблема кластера (5:30)
**Заголовок:** Кто собирает RSS?  
**Контент:**
- 3 ноды запущены одновременно
- Каждая хочет собрать новости
- Без координации → тройное дублирование

**Визуал:** 3 ноды, все тянутся к RSS → коллизия

---

## Слайд 7 — Решение: Distributed Lock (6:30)
**Заголовок:** `DistributedScheduler` — Redis NX Lock  
**Код (ключевой фрагмент):**
```typescript
const result = await redis.set(
  `lock:rss:${taskName}`,
  this.nodeId,
  { PX: 30000, NX: true }  // NX = только если не существует
);
```
**Визуал:** 3 ноды → только 1 получает lock → остальные пропускают

---

## Слайд 8 — Heartbeat (8:00)
**Заголовок:** Как ноды «видят» друг друга  
**Контент:**
- Каждые 10 сек → `heartbeat:{nodeId}` в Redis
- TTL = 45 сек → нода «умерла» если нет heartbeat
- Данные: CPU, RAM, WebSocket-соединения

**Визуал:** Timeline heartbeat-ов

---

## Слайд 9 — LoadBalancer (9:30)
**Заголовок:** Выбор ноды для задачи  
**Две стратегии:**
- **Round-robin** — по очереди
- **Least-loaded** — наименее загруженная (CPU × 0.7 + RAM × 0.3)

**Код:** `LeastLoadedStrategy.calculateLoadScore()`

---

## Слайд 10 — HealthCheckManager (11:00)
**Заголовок:** Мониторинг здоровья кластера  
**Статусы:**
- `healthy` — всё ок
- `degraded` — CPU > 80% или Redis недоступен
- `unhealthy` — БД недоступна или response > 5s

**Визуал:** Светофор статусов

---

## Слайд 11 — FailoverController (13:00)
**Заголовок:** Автоматический failover  
**Алгоритм:**
1. Нода стала `unhealthy`
2. Проверяем cooldown (5 мин) и rate-limit (3/час)
3. Выбираем лучшую целевую ноду
4. Освобождаем locks → уведомляем WS-клиентов → пишем в Redis

**Визуал:** Flowchart failover

---

## Слайд 12 — WebSocket в кластере (15:30)
**Заголовок:** Broadcast между нодами  
**Проблема:** Клиент подключён к ноде-1, событие на ноде-2  
**Решение:** Redis Pub/Sub → все ноды получают → рассылают своим клиентам  
**Код:** `webSocketManager.broadcastToCluster()`

---

## Слайд 13 — Nginx конфигурация (17:00)
**Заголовок:** Load Balancer для HTTP и WebSocket  
**Ключевые моменты:**
- `least_conn` для API
- `ip_hash` для WebSocket (sticky sessions)
- `proxy_next_upstream` — retry при ошибке
