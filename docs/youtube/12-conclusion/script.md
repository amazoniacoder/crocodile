**Эпизод 6 — PWA и офлайн.**

**Эпизод 7 — Безопасность.**  
Собственная CAPTCHA, DDoS-защита, Fail2Ban, SSL-мониторинг, AlertManager с 17 правилами. Enterprise-уровень без enterprise-бюджета.

**Эпизод 8 — Мониторинг.**  
`HealthMonitoringService`, `AlertManager`, `SlaMonitor`, `PrometheusMetrics`. Кабинет мониторинга с зонами A-C. Проактивный мониторинг — проблема обнаруживается до того, как её заметит пользователь.

**Эпизод 9 — База данных.**  
16 таблиц, GIN-индекс для полнотекстового поиска, триггер `tsvector_update`, архивирование статей старше 14 дней. Drizzle ORM — типобезопасные запросы без магии.

**Эпизод 10 — Deployment.**  
Native vs Docker, PM2 cluster, Nginx + SSL, многоэтапный Dockerfile. 2847 RPS на 4 GB RAM.

**Эпизод 11 — Масштабирование.**  
`DistributedScheduler` с Redis NX locks, `LoadBalancer` с least-loaded стратегией, `HealthCheckManager`, `FailoverController` с cooldown и rate-limit. Горизонтальное масштабирование встроено в код.

### Архитектурные решения

**[Экран: `lessons-learned.md` → раздел «5 ключевых решений»]**

Теперь о решениях, которые определили облик проекта.

**Решение 1: EventBus вместо прямых вызовов.**  
`CollectNewsUseCase` не знает о `ClusterNewsUseCase`. Он просто публикует `ArticlesCollected`. Это позволило добавлять новые обработчики без изменения существующего кода. ADR-0001.

**Решение 2: Drizzle вместо Prisma.**  
Drizzle — это TypeScript-first, SQL-first. Запросы читаются как SQL, но с полной типизацией. Нет магии, нет N+1 по умолчанию. ADR-0002.

**Решение 3: Wouter вместо React Router.**  
2 KB против 50 KB. Для SPA с простым роутингом — достаточно. ADR-0008.

**Решение 4: Redis NX для distributed locks.**  
Атомарная операция `SET key value NX PX 30000` — гарантия что только одна нода собирает RSS. Lua-скрипт для безопасного освобождения. Без этого — тройное дублирование статей в кластере.

**Решение 5: Двухуровневый кэш.**  
Redis → in-memory fallback. Если Redis недоступен — приложение продолжает работать. Graceful degradation на каждом уровне. ADR-0004.

**[Экран: `lessons-learned.md` → раздел «Что изменил бы сейчас»]**

Что бы я изменил сейчас? Три вещи.

Первое — `KEYS` в Redis. В нескольких местах используется `redis.keys('lock:rss:*')` — это O(N) операция, блокирует Redis при большом количестве ключей. В production нужен `SCAN`.

Второе — отсутствие read/write splitting для PostgreSQL. Сейчас все запросы идут на один инстанс. При наличии Patroni-кластера — читающие запросы можно направить на Slaves.

Третье — метрики. `PrometheusMetrics` есть, но нет Grafana-дашборда из коробки. Для нового разработчика — нужно настраивать с нуля.

### Честная оценка

**[Экран: `slides-outline.md` → Слайд 6 — Что хорошо / что улучшить]**

**Что сделано хорошо:**

Архитектура. DDD с чёткими слоями работает — можно добавить новый источник новостей, не трогая frontend. Можно заменить Redis на другой кэш, не трогая бизнес-логику.

Отказоустойчивость. Каждый компонент имеет fallback: нет Redis — работает in-memory, нет NER-сервиса — кластеризация по токенам, нет одной ноды — другие подхватывают.

Типизация. TypeScript везде, Drizzle даёт типы из схемы БД. Рефакторинг не страшен — компилятор поймает несоответствия.

**Что можно улучшить:**

Тесты. Покрытие есть, но интеграционных тестов для кластерного поведения нет. `FailoverController` тестируется только unit-тестами с моками.

Документация API. OpenAPI/Swagger нет — новый разработчик изучает API по коду или `DEVELOPER_GUIDE.md`.

Observability. Логи есть (Winston), метрики есть (Prometheus), но нет distributed tracing — сложно отследить запрос через все слои.

### Roadmap

**[Экран: `roadmap.md` → раздел «Ближайшие улучшения»]**

Куда двигаться дальше — три направления.

**Направление 1: Качество кода.**  
Заменить `KEYS` на `SCAN`, добавить интеграционные тесты для кластера, OpenAPI-документацию через `zod-to-openapi`.

**Направление 2: Observability.**  
Grafana-дашборд для Prometheus-метрик, distributed tracing через OpenTelemetry, structured logging с correlation ID.

**Направление 3: Новые функции.**  
Персонализированная лента на основе истории чтения (без профилирования — только локально в браузере), поддержка Atom-фидов, экспорт в OPML.

**[Экран: `roadmap.md` → раздел «Долгосрочно»]**

Долгосрочно — два больших направления.

Kubernetes вместо Docker Swarm. Helm-чарты, HPA для автоскейлинга, Istio для service mesh.

Многоязычность. Сейчас NER заточен под русский через pymorphy2. Добавить spaCy для английского — и агрегатор становится международным.
