## 🎯 Вызовы

### Вызов 1: onConflictDoNothing
**Время:** После объяснения дедупликации (11 минута)

```
🤔 Вопрос:

RSS-парсер собирает статьи каждые 5 минут.
Одна и та же статья может появиться в ленте
несколько раз подряд.

Как newsArticleRepository.insert() обрабатывает дубликаты?

A) Проверяет EXISTS перед INSERT — два запроса
B) onConflictDoNothing — один атомарный запрос
C) Бросает исключение, парсер его перехватывает
D) UPDATE вместо INSERT если URL уже есть

Почему B лучше A?
```

**Правильный ответ:** B — атомарная операция, нет race condition при параллельном сборе из нескольких источников. A создаёт окно между EXISTS и INSERT.

### Вызов 2: Двухуровневый кэш
**Время:** После объяснения Redis → in-memory (20 минута)

```
💾 Redis недоступен (ECONNREFUSED).
Что произойдёт с кэшем?

A) Приложение упадёт с ошибкой
B) Все запросы пойдут напрямую в БД (нет кэша)
C) Работает in-memory кэш (max 1000 записей)
D) Кэш отключается, но приложение работает

Что из этого ТОЧНО происходит в коде?
(подсказка: redis.ts + QueryCacheService.get())
```

**Правильный ответ:** C — `redisEnabled = false`, `getRedisClient() → null`, `QueryCacheService.get()` переходит к `memoryCache`. Приложение продолжает работать с локальным кэшем.

### Вызов 3: stale-while-revalidate
**Время:** После объяснения stale-while-revalidate (23 минута)

```
⏱️ Кэш настроен:
  ttl: 300 сек (5 мин)
  staleWhileRevalidate: 60 сек

Статья закэширована 90 секунд назад.
Пользователь делает запрос.

Что произойдёт?

A) Cache MISS — данные устарели (> 60 сек)
B) Cache HIT, X-Cache-Status: FRESH
C) Cache HIT, X-Cache-Status: STALE + удаление ключа в фоне
D) Cache HIT, немедленное обновление данных

Объясните разницу между TTL и staleWhileRevalidate.
```

**Правильный ответ:** C — 90 сек > staleWhileRevalidate(60), но < TTL(300). Данные отдаются немедленно (быстро для пользователя), ключ удаляется через setImmediate. Следующий запрос получит свежие данные.
